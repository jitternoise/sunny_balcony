# Flash Flood — Project Scaffold

A working Godot 4.6 skeleton for the hex-grid, tick-based water-diversion puzzle game. Opens and runs as-is with the **full 100-level campaign** authored, organized into 13 task-based groups (see "Campaign structure" below). Every level requires at least one player interaction -- a block placement or a dig tap -- and every level ships with a simulation-verified solution (`claude/level-solutions.md` in the project has the full table).

## How to open it

1. Install Godot 4.6 (or later 4.x) — godotengine.org/download
2. Open Godot, click **Import**, and select the `project.godot` file in this folder
3. Press **F5** (or the Play button) to run — it opens on the main menu

## What's implemented

- **Main Menu → Save Slot Select → Level Select → Level** navigation, all wired up
- **Level-intro popup**: the instant a level scene loads, a modal popup shows the level's name and a short description of what it does/teaches (`LevelData.intro_text`), with a single **Got it** button. Every other on-screen control -- Start, Retry, Back, the inventory bar, tapping the grid -- is unresponsive while it's up, since the popup's full-screen dim rect sits on top of and is hit-tested before everything else in the `UI` layer (see `UI/IntroPanel` in `Level.tscn`). Tapping Got it just hides the popup; it doesn't re-appear on an in-place Retry, only on actually (re-)entering the level scene. A level with no `intro_text` set skips the popup entirely.
- **Win popup**: replaces the old "auto-return to Level Select after a moment" behavior. The instant `HexBoard.level_won` fires, `Level.gd`'s `_on_level_won()` stops the tick timer and shows `UI/WinPanel` -- a modal popup reading **Success!** with a single button, labeled **Next** if a later level exists in `LevelSelect.LEVEL_PATHS`, or **Level Select** on the last level. Same full-screen-dim-rect-as-last-child-of-`UI` structure as `IntroPanel`/`LosePanel`, so it blocks every other on-screen control the same way. Tapping **Next** sets `GameState.pending_level_path` to the next entry in `LevelSelect.LEVEL_PATHS` and reloads `Level.tscn` from scratch -- which naturally re-runs `_ready()` and shows that next level's own intro popup, with no special-casing needed. Tapping **Level Select** (or **Next** on the final level) returns to the level picker instead.
- **Pre-start flow preview**: before Start is pressed, every water source shows a chain of up to 4 amber arrows tracing where its water would actually flow -- one hex-to-hex step per arrow, following the exact same natural-fall/block-redirect rules the real simulation uses, recomputed live every time a block is placed or removed (or a dirt cell is dug open -- see "Dig the River" below) so the preview always reflects the current board. A Splitter fans out into two separate arrow chains; a Wall, an undug dirt cell, or the grid edge quietly ends a chain (nothing useful to show past a dead end); a town, pool, or still-dormant geyser also ends a chain, but only after drawing the arrow *into* that cell, since "the water reaches this and stops" is worth showing. A fire cell is the one exception -- the chain draws an arrow into it but keeps going past it, since a fire only consumes the first drop that ever reaches it and every later beat passes straight through, so the preview shows where the water ultimately ends up rather than stopping dead at the first fire it touches. The preview disappears the instant Start is pressed (`HexBoard.show_flow_preview` flips to false and the board force-redraws right then, not on the next tick) and reappears on Retry. See "Pre-start flow preview" further down for the full writeup.
- **Sky-and-grass background**: every screen (Main Menu, Save Slot Select, Level Select, and in-level) now has a two-tone background instead of the engine's default flat grey -- a light blue "sky" band across the top 20% of the screen and a green "grass" band across the bottom 80%, both fixed screen-space rectangles that sit behind every other node. On the Level screen it's drawn on its own `CanvasLayer` (layer -1, below the board's layer 0 and the UI's default layer) so it stays put behind the hex grid even when a tall level is scrolled. See "Background" below for the exact colors/nodes.
- **3 save slots**, persisted to disk as JSON (`user://saves/slot_N.save`), tracking highest unlocked level and completed levels
- **Linear level unlock**: finishing a level unlocks the next
- **Hex grid** (axial coordinates) with a custom-drawn board, in either of **two orientations** per level (`LevelData.grid_style`, see below). Cells render as a colored polygon with an SVG icon glyph drawn on top (`assets/icons/`) — every placeable block type and the Fire/Pool/Town/Source terrain types have a dedicated icon; Geyser still uses a small procedural droplet shape since no SVG asset exists for it yet, and Dirt deliberately has no glyph (its dig progress is communicated purely through color stages -- see "Dig the River" below).
- **Two grid orientations**: `"pointy"` (the original grid, default) has pointed top/bottom vertices and no direct-down neighbor, so unblocked water naturally zigzags between its two down-diagonals. `"flat"` is the rotated variant added this session — a flat bottom EDGE gives a genuine direct-down neighbor (`Hex.FLAT_DOWN`), so a `"flat"`-level water source can be configured to fall straight down instead of zigzagging. Set per-level via `LevelData.grid_style`; `Hex.gd`'s pixel/corner math, `HexBoard`'s simulation, and the Level Select/tap-to-place input all adapt automatically based on it -- see "Two grid orientations" further down for the full mechanical writeup, and Level 20 for a working demo.
- **4 sample block types** (Wall, Diverter-Left, Diverter-Right, Splitter) as data-driven `.tres` resources under `data/blocks/` — add a new block type by duplicating one of these files, no code changes needed. The same four blocks work on either grid orientation: Diverter-Left/Diverter-Right/Splitter resolve to whichever direction "down-left"/"down-right" actually means for that level's grid (see `HexBoard._resolve_block_targets()`) rather than needing separate "flat" versions of each block.
- **Fires and pools**: water extinguishes fire cells; pools finish once water has been connected to them for 4 beats, shown via a 4-box status bar that pops up above the pool on its first connected beat (see below) — winning requires all fires out and every pool's bar fully lit
- **Towns**: an instant-loss hazard. A town is one or more axial coordinates (`LevelData.town_cells`, authoring convention: exactly 4 edge-connected hex cells in whatever shape fits the level) rendered with a house icon. Water reaching **any** town cell ends the level in a loss immediately, same as flooding past the bottom edge. Blocks can't be placed on a town cell (same rule as fire/pool cells). The specific town cell water actually reached turns light blue (`HexBoard.flooded_towns`) instead of its usual brown, so the board's final frame visibly marks exactly where the flood hit.
- **"Dig the River" levels**: a level can declare packed-dirt cells (`LevelData.dirt_cells`). An undug dirt cell behaves exactly like a permanent Wall toward water -- natural fall can't land on it (the stream retries its other diagonal, and if everything is blocked the water backs up and waits -- but see the **Mudslide** bullet below: it won't wait forever), forced block redirects can't push water into it, and no block can be placed on it. The player digs a dirt cell open by **tapping it 3 times** (`HexBoard.DIG_TAPS_REQUIRED`, via `HexBoard.dig()`, wired into `Level.gd`'s tap handler ahead of block placement/pickup) -- free, unlimited, any time before or after Start. Progress feedback is **color stages only** (a deliberate design choice -- no status bar or counter): packed dark earth at 0 taps, progressively lighter at 1 and 2 (`HexBoard.DIRT_COLORS`), and once opened the cell becomes ordinary empty terrain drawn in a distinct trench color (`DUG_TRENCH_COLOR`) so the carved channel stays readable as "riverbed." Digging takes effect immediately (not deferred to the PLACEMENT beat like blocks) -- the water is released the instant the third tap lands -- and pre-start digging live-extends the amber flow-preview arrows through the freshly opened cell. Retry resets every dirt cell back to fully undug. Level 21 is the first example: the whole lower board is dirt and the player must tap the river's channel forward all the way down to the pool.
- **Mudslides**: dirt holds the river back, but not forever. Once a water drop has spent `MUDSLIDE_BEATS_REQUIRED` (10) consecutive WATER beats pressing against undug dirt (~3 seconds at the current tempo), the dirt gives way: a chain of `MUDSLIDE_COLLAPSE_TILES` (3) dirt tiles collapses downward, starting with the blocking tile and continuing in the slide's direction (falling back to the grid's other downward option when the preferred one isn't dirt; the chain stops early if no dirt continues it). Collapsed tiles open fully -- water floods through on the very next beat -- and are drawn in a distinct wet-mud color (`MUDSLIDE_COLOR`, darker than the player-dug trench color), so the board shows where the river forced its own path versus where the player chose it. The stall clock (`HexBoard.dirt_stall`) only counts *unbroken* stalls: the moment the water moves on (e.g. the player digs the blocker open in time) the counter for that cell resets, and a drop still stuck after a slide starts a fresh 10-beat clock toward the next one. Ordinary Wall/edge backups never slide -- only dirt does. Net effect on dig levels: idling is no longer safe. On level 21, pressing Start and doing nothing now ends with the river carving its own path off the board (verified: edge loss on measure 29 after 2 slides); the player's job is to stay ahead of the water.
- **Preset blocks** (`LevelData.preset_blocks`): a level can ship with blocks already installed on the board as fixed terrain -- an axial-coordinate -> block-id map, committed straight into `placed_blocks` at `setup()`. They're live from the first beat, cost no inventory, render and simulate exactly like a player-placed block of the same id, but can't be picked up (`remove_block()` refuses, same as tapping a fire/pool). Retry restores them automatically since `setup()` re-runs. Level 22 uses this for its cascade of 10 fixed Splitters.
- **Corridor levels as a first-class field** (`LevelData.corridor_half_width`): when > 0, the playable area is restricted to a vertical band `half_width` cells to each side of `q = round(-r/2)` per row -- the same visually-vertical band rule levels 13-17 hand-carved with `blocked_cells`, now one field. Required for very deep levels: level 22's radius-50 grid would otherwise need ~7,000 `blocked_cells` entries, bloating the file and making `in_playable_area()`'s per-cell-per-redraw `Array.has()` check unusably slow. 0 (default) disables it; composes with `blocked_cells`.
- **Source-cell placement ban + 2-row clearance rule**: player blocks can never be placed ON a water source cell -- an original `water_sources` entry or an activated geyser (`HexBoard.place_block()` rejects both, same as tapping a fire/pool). Companion authoring rule (enforced by audit, not code): no PREPLACED level tile -- fire, pool, town, geyser, dirt, or preset block -- may sit within 2 rows vertically of a starting water source (`|r_tile - r_source| >= 2`); `blocked_cells` (grid shape) are exempt. All 22 levels were audited against both rules; levels 2/4/8 had a fire moved down a row, level 12 was relaid, level 22's dirt now starts 2 rows below its source, and levels 1/10/11/12's old solutions (a diverter placed directly on the source) were replaced with the **Wall-at-first-landing** technique: a Wall on the cell the source's first drop lands on bounces the stream onto the right-hand column (`q` unchanged), reaching cells the natural leftward drift never could -- the new standard way to stabilize a stream now that the source cell itself is off-limits.
- **Lose condition**: water reaching the bottom edge of the grid, or reaching a town cell -- `HexBoard.lose_reason` records which one happened (`LoseReason.EDGE` / `LoseReason.TOWN`). On loss, `Level.gd`'s `_on_level_lost()` stops the tick timer and pops up a small modal panel (`UI/LosePanel`) over a dimmed background with a reason-specific message and two buttons, **Retry** and **Level Select** -- the always-visible HUD Retry/Back buttons at the top keep working too, this popup is just the primary, hard-to-miss prompt at the moment of failure.
- **Real-time block placement and removal**: blocks can be placed AND picked back up at any time, including while water is actively flowing mid-simulation -- placement was never actually gated on the Start button, and removal (tap a placed block to pick it up, refunding it to inventory) now works the same way. There's no separate "planning phase"; Start just controls whether the tick timer is running.
- **In-level Retry button**: next to Start, resets the current level in place (`board.setup()` re-run, timer stopped, inventory/terrain/water all back to the level's starting state) without leaving the scene -- no round trip through Level Select needed after a loss (or to restart mid-attempt). The lose popup's own Retry button calls the exact same reset function, and the win popup is also hidden on retry (`win_panel.visible = false`).
- **Limited per-level inventory**: each level defines how many of each block the player starts with; the bottom UI bar shows remaining counts and disables exhausted blocks
- **Screen-filling, scalable grid**: every level's hex grid always renders at exactly 90% of the screen's width (5% margin on each side) with its top edge 10% of the way down the screen, regardless of `grid_radius` -- tile size is solved for per level (`HexBoard._fit_hex_layout()`), not fixed, so a small grid and a large one both fill the same width, just with different tile sizes. Works identically for either grid orientation.
- **Tall scrolling levels**: a grid can be narrow (staying within the 9-tile-wide cap) while still being many rows tall -- once the grid's height at the solved tile size exceeds what fits below the top margin, the player can drag (or scroll the mouse wheel, for desktop testing) to reveal the rest (`HexBoard.max_scroll_down`, handled by `Level.gd`'s press/drag/release input tracking, which distinguishes a real drag from a tap so scrolling and block placement/removal don't interfere with each other). Levels 13-17 are built this way -- tall, narrow corridors requiring scrolling to see the whole level.
- **Water source markers**: every source cell (a `water_sources` entry, or a geyser once it activates -- see below) is marked with the river icon plus a bright ring and a small arrow showing the direction its very first drop will fall -- on a `"flat"` level this correctly points straight down or down-left depending on that source's flow style (see `HexBoard._first_move_direction()`). Drawn every frame regardless of whether water currently occupies the cell, so the source's location and first-move direction are always visible, not just while a drop is sitting there.
- **Geysers**: a dormant terrain type that needs exactly `GEYSER_BEATS_REQUIRED` (3) beats of water connection -- same fixed-requirement, cumulative-progress pattern as a Pool's 4-box bar, shown the same way but with 3 boxes -- before it activates. Once activated, its terrain reverts to empty (it stops consuming water) and its coordinate is added permanently to `HexBoard.active_geysers`, which spawns a brand new independent falling stream from that cell every tick from then on, exactly like one of the level's original `water_sources` -- letting a level introduce a *second* source partway down the board instead of only at the top. Rendered as a small purple upward-spraying-droplet icon while dormant; gets a source marker + direction arrow of its own once active. Blocks can't be placed on a geyser cell (same rule as fire/pool/town). On a `"flat"` level, an activated geyser always flows `"straight"` (not configurable per-geyser yet). **Once activated, the geyser cell itself permanently blocks the ORIGINAL stream that fed it into activation** -- `HexBoard._is_wall()` treats any coordinate in `active_geysers` exactly like a placed Wall block, so any later beat from the level's original `water_sources` that would otherwise walk straight into that now-empty cell instead backs up and reroutes via its other diagonal there, same as hitting any ordinary Wall. The geyser's own newly-spawned stream is unaffected (it's injected directly each tick, bypassing that check). See "Geysers" further down for the full writeup.
- **"Jamboree" levels**: an alternate inventory mode for a level, switched on by setting `LevelData.total_block_budget` to a positive number instead of using `starting_inventory`. Instead of a fixed count *per block type*, the player draws from one shared pool of that many total placements and can freely place **any** block type from the full catalog in any combination -- 3 Walls, or 2 Diverters and a Splitter, whatever the budget allows. `HexBoard.use_block_budget` / `block_budget_remaining` track this at runtime (`inventory` is left empty and unused in this mode); `Level.gd`'s inventory bar switches to showing every catalog block (not just the level's `starting_inventory` keys) with a shared "Tiles left: N" counter (`UI/HUD/BudgetLabel`) instead of a per-button count, and every button disables together once the pool hits zero. Level 19 is the first example.
- **100 levels** (`data/levels/level_001.tres` through `level_100.tres`), each with a descriptive `display_name` and an `intro_text` blurb. Levels 1-22 are the hand-built originals; levels 23-100 were generated programmatically (solution-first templates + rejection sampling) and every one of the 100 -- parsed back from the shipped `.tres` files, not the generator's memory -- passes the full validation battery: its documented solution wins, a zero-interaction run NEVER wins (so at least one tap/placement is always genuinely required), all preplaced tiles respect the 2-row source clearance, and no placement touches a source. The Level Select screen shows a header row above each task group (see `LevelSelect.GROUPS`).
- **Campaign structure (13 task groups)**: Riverbed Basics 1-12 (diverters, walls, splitters, towns -- the original teaching levels), Long Corridors 13-17 (scrolling), Special Waters 18-20 (geyser / jamboree / flat grid), Dig the River 21-22 (digging + the splitter cascade), Diverter Drills 23-30, Wall Work 31-38, Split Networks 39-46, Town Defense 47-54, Flat Fields 55-62 (flat grid), Geyser Country 63-70, Big Digs 71-78 (dig levels up to 25-row corridors), Jamboree Runs 79-86 (shared block budgets on corridors), and The Gauntlet 87-100 -- escalating corridor levels mixing everything: solution blocks, fixed preset splitters, dirt bands to dig through, towns, geysers, and budgets, growing from radius 10 to radius 20.
- **Every level requires interaction**: the eight original "just watch" levels (2, 4, 6, 8, 9, 13, 18, 20) were retrofitted -- each now needs exactly one block placement (the pools were re-placed off the natural path via simulation search, keeping each level's original teaching subject: the hole-bounce on 6, the twin sources on 9, the geyser on 18 -- verified to still activate -- and the flat grid on 20)
- **Debug mode**: a "Debug: Unlock All" checkbox on the Level Select screen (top-right) makes every level selectable regardless of save progress. It's on by default when running from the editor or a debug export (`OS.is_debug_build()`), off by default in a release export -- but can be toggled either way at runtime. It's a session-only flag (`GameState.debug_unlock_all`): it never touches `highest_unlocked_level`/`completed_levels` and is never written to a save file, so toggling it can't corrupt real progress, and it resets to the build-type default next launch.

## Background

Every screen has a fixed two-tone background: a light blue **Sky** rectangle covering the top 20% of the screen, and a green **Grass** rectangle covering the bottom 80%, replacing the engine's default flat grey. Implemented as two plain `ColorRect` nodes per scene (`Sky`: `anchor_bottom = 0.2`, `Grass`: `anchor_top = 0.2`, both `anchor_right = 1.0`/`anchor_bottom` as needed, `mouse_filter = 2` so they never intercept clicks), colors `Color(0.53, 0.81, 0.92, 1)` (sky) and `Color(0.3, 0.69, 0.31, 1)` (grass).

- On the three `Control`-rooted UI scenes (`MainMenu.tscn`, `SaveSlotSelect.tscn`, `LevelSelect.tscn`), the `Sky`/`Grass` `ColorRect`s are the first two children of the scene root, so ordinary node draw order puts them behind every other UI element.
- On `Level.tscn` (a `Node2D`-rooted scene whose `Board` node can scroll on tall levels), the same two `ColorRect`s live under a dedicated `Background` `CanvasLayer` with `layer = -1` instead -- `CanvasLayer` draw order is controlled by its `layer` number rather than child order, so `layer = -1` guarantees it renders behind `Board` (layer 0) and `UI` (default layer) regardless of node order in the scene, and because it's a `CanvasLayer` (not a child of `Board`) it stays fixed to the screen rather than scrolling along with the hex grid.
- The hex grid's own empty-cell fill color (`HexBoard._draw_cell()`'s `Color(0.15, 0.15, 0.18)` dark grey default) is unchanged -- that's the tile color for unoccupied playable cells within the grid itself, a separate thing from the screen background behind the whole board.

**Not yet done:** like the rest of this session's rendering work, this hasn't been visually confirmed in a live Godot window yet -- added to "Known gaps" below.

## Level-intro popup (`intro_text`)

Every level has a short `LevelData.intro_text` string describing what it does or teaches -- the mechanic/hazard in play, deliberately NOT the exact solution or block placements. The instant `Level.gd`'s `_ready()` finishes building the inventory bar, `_show_intro_popup_if_needed()` checks this field: if it's non-empty, it shows `UI/IntroPanel` (title = the level's `display_name`, body = `intro_text`) with a single **Got it** button; an empty `intro_text` (the field's default) skips the popup entirely.

`IntroPanel` is structured identically to the existing `LosePanel` -- a full-screen dimmed `ColorRect` (`mouse_filter = 1`, i.e. `MOUSE_FILTER_STOP`) plus a centered `PanelContainer` -- and is added as the LAST child under the `UI` `CanvasLayer`, so Godot draws it on top of, and hit-tests it before, every other UI node. That's what makes "every other button is unresponsive until Got it is tapped" actually true rather than just a visual layer: any tap/click anywhere on screen while the panel is visible is consumed by its dim rect and never reaches the Start/Retry/Back buttons, the inventory bar, or the board underneath. Tapping Got it just sets `intro_panel.visible = false`.

The popup does NOT re-appear on an in-place Retry (`_on_retry_pressed()` deliberately doesn't call `_show_intro_popup_if_needed()` again) -- the player has already seen and acknowledged it for this visit to the level scene; only actually re-entering the scene (e.g. from Level Select) shows it again.

## Win popup (`UI/WinPanel`)

On a win, `Level.gd`'s `_on_level_won()` (connected to `HexBoard.level_won`) stops the tick timer, marks the level complete in `GameState`, and shows `UI/WinPanel` instead of the old behavior of auto-returning to Level Select after a fixed delay. `WinPanel` is structured exactly like `IntroPanel`/`LosePanel` -- a full-screen dimmed `ColorRect` plus a centered `PanelContainer` -- and is the LAST child under `UI` (after `IntroPanel`), so it draws on top of and is hit-tested before everything else, same blocking guarantee as the other two popups.

The panel's single button is relabeled at win time by `_on_level_won()`: **Next** if `_next_level_path()` (a lookup into `LevelSelect.LEVEL_PATHS`, found via `class_name LevelSelect` added to `scripts/ui/LevelSelect.gd` specifically so `Level.gd` can reference that array without needing a `LevelSelect` scene instance) finds a later level, or **Level Select** if the current level is the last one in the array. Tapping the button (`_on_win_next_pressed()`) either sets `GameState.pending_level_path` to the next level's path and reloads `Level.tscn` -- which naturally re-runs `_ready()` from scratch, so the next level's own intro popup shows automatically with no special-casing -- or, on the last level (or if the button reads Level Select), just returns to `LevelSelect.tscn`.

`win_panel.visible` is also reset to `false` in `_on_retry_pressed()`, alongside `lose_panel`, so an in-place Retry after a win (not a normal flow, but reachable via the HUD's always-visible Retry button) doesn't leave a stale popup on screen.

## Pre-start flow preview

Before the player presses Start, `HexBoard._draw()` shows a forecast of where each `water_sources` entry's water will actually flow, so the player can see the effect of a block placement before committing to it (no need to actually watch it play out or reason through the zigzag by hand). Controlled by `HexBoard.show_flow_preview` (default `true`, reset to `true` by every `setup()` call -- i.e. on level load and on Retry) -- `Level.gd`'s `_on_start_pressed()` sets it to `false` and calls `board.queue_redraw()` immediately, so the arrows vanish the instant Start is tapped rather than lingering until the first tick ~0.6s later.

The preview is computed by `HexBoard._predict_flow_arrows()` / `_predict_branch()`, a read-only forecast that walks up to `PREVIEW_ARROW_STEPS` (4) hex-to-hex moves per source, following the *exact same* natural-fall and placed-block-redirect rules `_advance_water()`/`_advance_water_flat()` use (including all of `_is_wall()`'s geyser- and dirt-blocking and the flat grid's boundary-vs-blocked_cells distinction) -- it's not a separate/approximate model, it's the real decision logic run against a hypothetical walk instead of the live simulation. Critically, it never touches real game state: terrain checks go through a new read-only `_predict_would_consume()` instead of `_try_enter()`, so computing (and recomputing, live, on every block placement pre-start) a preview can never actually consume a fire, fill a pool, charge up a geyser, or trigger a win/loss.

- **A Splitter branches the forecast into two chains**, one per target direction, each independently walking its own remaining steps.
- **A Wall, an undug dirt cell, a boxed-in dead end (blocked on every candidate direction), or an edge exit all silently end a chain** with no further arrow -- there's nothing useful to draw past any of them. Because an undug dirt cell ends a chain the same way a Wall does, digging one open pre-start immediately EXTENDS the preview through it on the next redraw -- the player can watch their channel's forecast grow tap by tap ("Dig the River" levels).
- **A town, pool, or still-dormant geyser cell also ends a chain, but only after drawing the arrow *into* it** -- unlike the cases above, "the water reaches this and stops flowing" (an instant loss, a pool that will consume every later beat too, or a geyser that isn't active yet) is exactly the kind of outcome worth showing the player before they commit to a placement.
- **A fire cell is deliberately the one exception that does NOT end a chain.** A real fire cell only consumes the *first* water that ever reaches it, then reverts to empty terrain and lets every later beat pass straight through untouched (see "Notes on the current simulation model" below). Since the preview is meant to forecast where a solution's water ultimately ends up -- not literally "what happens to one single drop" -- it draws the arrow into the fire cell and keeps going, so a level like 12 (Town Alert) shows its full source-through-redirect-through-fire-into-pool chain in one glance instead of stopping dead at the first fire cell.

Rendered by `_draw_flow_preview()`/`_draw_flow_arrow()`: same line-plus-two-stroke-arrowhead style as the small white first-move arrow already drawn on every source marker, just in amber and fading slightly dimmer step-by-step so the chain reads as a directional trail. `_draw_source_marker()` skips its own small arrow entirely while the preview is showing (`show_flow_preview == true`), since the preview's first segment already covers that exact same first move in more detail -- the source's ring and river icon still draw either way, and the small arrow resumes as normal once Start is pressed and the preview disappears.

This was verified with a from-scratch Python port of `_predict_branch()`/`_predict_flow_arrows()` against several levels' actual data (12, 1, 7, 20) -- confirming an unsolved Level 12 correctly stops its single arrow at the town, a solved Level 12 (diverter placed) correctly chains all the way through the fire into the pool in exactly 4 arrows, Level 7's Splitter correctly produces two branches, and Level 20's flat-grid straight/zigzag sources trace the right columns/diagonals. Not yet visually confirmed in a live Godot window, same caveat as everything else in this project to date -- see Known gaps.

## Two grid orientations (`grid_style`)

Every level picks its hex orientation via `LevelData.grid_style`, `"pointy"` (default) or `"flat"`. This is set once per level, into `Hex.orientation`, by `HexBoard.setup()` -- from that point on, every `Hex.axial_to_pixel()`/`Hex.hex_corner()`/`Hex.pixel_to_axial()` call (rendering, `_fit_hex_layout()`'s sizing, tap-to-place input) automatically uses the right pixel math and corner angles for that orientation. No other code needs to know or care which orientation is active.

- **`"pointy"`** (unchanged from before this session): pointed top/bottom vertices, flat left/right sides. There's no direct "straight down" neighbor -- the bottom of the hex is a vertex, not an edge -- so unblocked water always zigzags between its two down-diagonals (`Hex.DOWN_LEFT`/`Hex.DOWN_RIGHT`), retrying the other one if the first is blocked by a Wall or the grid edge. This is the entire simulation model documented in "Notes on the current simulation model" below, and every one of levels 1-19's `.tres` files use it. **This orientation's code path (`HexBoard._advance_water()`'s non-flat branch, `_try_natural_step()`) is completely untouched by the "flat" work below** -- it's a fully separate function, specifically so the new grid type can't regress any of the already-verified pointy levels.
- **`"flat"`** (new): rotated 90 degrees -- flat top/bottom EDGES, pointed left/right vertices. This gives a genuine direct-down neighbor, `Hex.FLAT_DOWN`, which is the whole point of this variant: a water source can fall straight down a column instead of always having to zigzag. Handled by its own function, `HexBoard._advance_water_flat()`.
  - **Per-source flow style**: `LevelData.source_flow_style` is a `Vector2i -> String` map (water source coordinate -> `"straight"` or `"zigzag"`, defaulting to `"straight"` if a source isn't listed). Different sources on the same `"flat"` level can use different styles -- see Level 20, which has one of each. A `"straight"` source only ever tries `Hex.FLAT_DOWN`; a `"zigzag"` source alternates between the true down-left/down-right diagonals (`Hex.FLAT_DOWN_LEFT`/`Hex.FLAT_DOWN_RIGHT`), mirroring the pointy grid's zigzag but with this grid's own diagonal pair -- note this pair doesn't drift the way the pointy grid's zigzag does (see the code comment on `_advance_water_flat()` for why), it's a symmetric left-right oscillation instead. Active geysers on a `"flat"` level always use `"straight"` (not exposed as configurable per-geyser).
  - **Placed blocks work the same way as pointy** -- no new "flat" block types were added. Diverter-Left/Diverter-Right/Splitter conceptually always mean "send water down-and-to-the-left/right"; `HexBoard._resolve_block_targets()` just resolves that to whichever grid's actual directions apply (`Hex.DOWN_LEFT`/`DOWN_RIGHT` for pointy, `Hex.FLAT_DOWN_LEFT`/`FLAT_DOWN_RIGHT` for flat). One thing worth knowing: on a `"flat"` level, Diverter-Right sends water via the grid's TRUE down-right diagonal (`Hex.FLAT_DOWN_RIGHT`, a `(1,0)` axial step) which is a *different* direction than a `"straight"` source's own natural fall (`Hex.FLAT_DOWN`, a `(0,1)` step) -- so placing a Diverter-Right on a `"flat"` level genuinely reroutes a stream sideways, it doesn't just confirm the straight-down direction.
  - **Loss detection had to be generalized for this grid.** The pointy grid's "hit the true bottom edge = instant loss" shortcut relies on both its down-diagonals always increasing `r` by exactly 1 -- that's not true for `Hex.FLAT_DOWN_RIGHT` (a pure `q+1` step, `r` unchanged), so `_advance_water_flat()` instead checks each candidate direction directly against the grid's cube-coordinate radius (`HexBoard._cube_distance()`), independent of which axis the exit happens through, and only triggers a loss once *every* candidate direction for that stream has failed *and at least one of them failed specifically by exiting the level's true boundary* (as opposed to being blocked by a `blocked_cells` corridor wall, which just makes the water back up and pool the same way a Wall block would). This was verified against a from-scratch Python port of the new logic (see Level 20's playtesting note) before being written into `HexBoard.gd`.

## Adding content

- **New block type**: duplicate a file in `data/blocks/`, change `id`, `display_name`, `behavior` (see the `TickBehavior` enum in `scripts/resources/BlockData.gd`), `color`, and (optionally) `icon` -- point it at a `Texture2D` under `assets/icons/` (an `ext_resource` entry plus `icon = ExtResource("N")` on the resource, see any existing block `.tres` for the pattern) to get a glyph drawn automatically; leave it unset and the block just falls back to its flat `color` fill with no glyph. It's picked up automatically — Level.gd loads every `.tres` in that folder at runtime. Works on either grid orientation with no extra work (see "Two grid orientations" above).
- **New level**: duplicate `data/levels/level_001.tres`, edit its fields (grid size, water sources, fires, pool targets, starting inventory, `display_name` -- give it a real name, not just "Level N", e.g. `"22. Something"` -- and `intro_text`, a sentence or two describing the mechanic without spoiling the exact solution), then add its path to the `LEVEL_PATHS` array at the top of `scripts/ui/LevelSelect.gd` (and extend a `GROUPS` entry if it belongs to a new task group). That array is the single source of truth for level order, and it's also what the win popup's **Next** button walks through to find the following level. Keep the grid's actual playable width at or under 9 tiles (see "Grid sizing/positioning" below) -- a small `grid_radius` (like levels 1-12, all radius 4) gives this for free since the whole diamond-shaped grid is the playable area; a tall, narrow level (like levels 13-17, 19) uses a bigger `grid_radius` for more rows but carves the playable area down to a narrow band with `blocked_cells`, so width stays capped even though the grid itself is tall.
- **New "Jamboree" level**: same as above, but leave `starting_inventory` empty and set `total_block_budget` to however many total block placements the level should allow. There's no per-type inventory to design around -- the solution just needs to work with *some* combination of blocks from the catalog totalling that many or fewer placements.
- **New "flat"-grid level**: set `grid_style = "flat"` and (optionally) fill in `source_flow_style` per water source coordinate (`"straight"` or `"zigzag"`, defaults to `"straight"` if omitted) -- see Level 20. Everything else about authoring a level (fires, pools, town, blocked_cells, starting_inventory) works exactly the same as a `"pointy"` level; only the natural-fall behavior and the grid's visual rotation differ.
- **New "Dig the River" level**: fill in `dirt_cells` with the packed-dirt coordinates (see Level 21 -- the simplest robust pattern is "everything below row N is dirt except the pool and any fires," so the ONLY way down is a channel the player digs, and the only real failure mode is digging a channel that reaches the bottom edge somewhere other than the pool). Dirt composes freely with every other mechanic -- blocks, fires (leave a fire cell out of `dirt_cells` and the dug channel can route through it), towns, geysers, either grid orientation. A level that's all-dirt-below needs no `starting_inventory` at all; digging is always free and unlimited. Water waiting against dirt backs up rather than losing, but only for `MUDSLIDE_BEATS_REQUIRED` (10) beats at a stretch -- then a mudslide collapses 3 tiles and the river routes itself (see the Mudslides bullet in What's implemented). Stakes come both from where the player chooses to dig and from keeping ahead of the slide clock.
- **New level with preset blocks / a deep corridor**: fill `preset_blocks` (coordinate -> block id from `data/blocks/`) to bake machinery into the board as fixed terrain, and set `corridor_half_width` instead of hand-listing `blocked_cells` for any level more than ~25 rows deep. Two authoring rules learned building level 22: (1) a pool must NEVER be a direct down-neighbor of a cell water flows *through* -- a pool consumes every stream forever, so it silently starves everything downstream of it; give each mid-level pool its own dead-end spur at least 2 columns off the main flow. (2) After a splitter, keep the continuing channel from drifting back toward the side branch for a couple of rows, or the two paths re-collide.
- **Real art**: blocks/terrain now render as a flat colored hexagon with an icon glyph drawn on top (`HexBoard._draw_cell()` / `_draw_icon()`) -- see `assets/icons/` for the current SVG set and `claude/icon-system.md` for the design rationale. Swapping in a different/upgraded icon is just replacing (or adding an `icon` field to) the relevant `.tres`/texture reference; no further code changes needed. Geyser is the one type still using a procedural shape (`_draw_geyser_icon()`) since it has no SVG yet; Dirt has no glyph by design (color stages only).
- **Background colors**: change the `color` value on the `Sky`/`Grass` `ColorRect` nodes in any scene's `.tscn` file (see "Background" above), or the split point by changing both rects' `anchor_bottom`/`anchor_top` (currently 0.2, an 80/20 grass/sky split) -- no code changes needed, it's pure scene data.
- **Intro popup text**: set/edit a level's `intro_text` field directly on its `.tres` (see "Level-intro popup" above) -- no code changes needed. Leaving it empty (the default) skips the popup for that level entirely.

## Notes on the current simulation model (pointy grid)

- Water moves downward on a pointy-top hex grid via its two "down" neighbors (r+1): down-left and down-right. A cell's own contents (empty vs. a placed block) decide where water goes *from* that cell each tick — a Wall blocks flow entirely (water backs up and pools against it), Diverters send it to one specific down-neighbor, and a Splitter sends it to both.
- **Natural fall is a zigzag, not straight down**: when a water cell has no block on it, it alternates down-left, down-right, down-left, ... on its own independent counter — each water stream (including each new drop spawned every tick at a source) tracks its own alternation state, so multiple streams can be out of phase with each other. A freshly spawned drop's first move is always down-left.
  - If a stream's required diagonal is blocked (off the grid edge, or a **Wall** block sits there), it tries the *other* diagonal that same tick instead. If both are blocked, the water just stays put and pools up there for that tick. Either way, the alternation counter still advances for next tick.
  - Only a Wall actually obstructs natural fall this way (an activated Geyser, and a still-undug Dirt cell on a "Dig the River" level, are also treated as Walls for this purpose -- see "Geysers" below and the "Dig the River" bullet in What's implemented). A **Diverter** or **Splitter** is a pass-through: natural-falling water lands on it just fine (it's not treated as "blocked"), and *that* block's own behavior then decides where it goes the following tick — same as it always has, since a cell's own contents (not the cell it's about to enter) determine its exit direction.
  - This only applies to the natural (unblocked) fall step. A cell a stream is currently *sitting on* always behaves per that cell's block (Wall/Diverter/Splitter) if it has one, overriding the zigzag outright with no retry logic. One dirt-specific nuance: a Diverter/Splitter whose forced target(s) are still undug dirt skips those targets like Walls, and if EVERY target is undug dirt the water backs up on the block itself until the player digs one open (see `_advance_water()`'s block branch).
- **Pool status bar**: each pool needs exactly 4 beats of water connection to finish (`HexBoard.POOL_BEATS_REQUIRED`), not a per-level configurable count. A 4-box bar is drawn above the pool's hex cell; it stays hidden until water first connects, then one box lights up per beat the water is connected. Progress is cumulative and preserved — if the stream is diverted away for a few beats, the boxes already lit stay lit, and connecting again just continues from where it left off (no reset to zero). `LevelData.pool_targets`'s stored int value is now vestigial (kept only so old level files still parse); only the dictionary's keys (which cells are pools) are read.
- **Towns**: instant loss, checked the same way fire/pool terrain is -- see `_try_enter()` in `HexBoard.gd`. A water stream sitting on a Diverter/Splitter that routes into a town cell loses exactly like natural fall walking into one; there's no special-casing, town is just another terrain type `_try_enter()` recognizes. The specific cell water reached is tracked in `HexBoard.flooded_towns` and rendered light blue instead of brown from that point on.
- A block sitting on a fire/pool/town cell it routes water into (e.g. a Diverter whose forced target is the fire) is correctly treated as "handled" even though the water gets consumed there -- an earlier version of this code mistakenly treated that as "the water didn't move" and re-added it at its own cell for a spurious extra tick, corrupting that stream's zigzag alternation timing on anything placed one step before a fire/pool. Fixed in `_advance_water()`'s block-handling branch.
- This was validated by running the project headlessly (no display) through Godot's own engine and confirming the menu flow and a full multi-tick simulation run with no script errors.
- Tick rate is controlled by `TICK_INTERVAL` at the top of `scripts/gameplay/Level.gd` (currently 0.6s) — adjust for pacing/feel.
- **Grid sizing/positioning**: `HexBoard.gd`'s `_fit_hex_layout()` (called from `setup()`) measures the level's hex grid's actual *playable* cells (respecting `blocked_cells`, not just the raw `grid_radius` diamond) at a reference tile size, then solves for the actual `Hex.SIZE` that makes that playable area's bounding box exactly 90% of the viewport's width, and positions the board (`self.position`) so its top-left bounding corner lands at the 5%-from-left / 10%-from-top point. `Hex.SIZE` is a mutable static (not a const) specifically so this can rescale it per level -- safe because only one `HexBoard` is ever on screen at a time. Level-design convention: keep the playable area's width at or under 9 tiles, and use `blocked_cells` to carve a level's shape down to that width regardless of `grid_radius` -- see "Tall, narrow corridor levels" below for how levels 13-17 do this to get scrolling, tall levels within the same width cap.
- **Tall, narrow corridor levels (13-17)**: built by picking a `grid_radius` big enough for the desired number of rows (more rows = taller), then blocking every cell outside a narrow vertical band with `blocked_cells`. The band isn't a constant-`q` slice (that's actually a *diagonal* parallelogram on screen, since a pointy-top hex's screen x is `sqrt(3) * (q + r/2) * SIZE` -- q alone doesn't track a fixed screen column as r changes). Instead each row's allowed `q` range is centered on `round(-r / 2.0)`, which keeps the band visually straight and vertical on screen as r increases. A half-width of 2 (5 tiles wide) was used throughout levels 13-17. One neat side effect: because the corridor is exactly as wide as the natural zigzag's drift, the water usually never even touches the corridor's blocked edges -- it just rides straight down the middle, the same way it would on an unbounded grid, so these levels play like a long version of the non-scrolling ones rather than introducing a new "bounce off the wall" mechanic (level 6 already covers that with a single blocked cell).
- **Pools must be the last stop on a stream's path.** Unlike Fire (which clears after the first stream reaches it, letting every later stream pass straight through), a Pool consumes every stream that reaches it, forever -- so anything placed further down the same corridor after a Pool would never receive water again. Levels with multiple pools on one source (9, 11, 15, 17) always put each pool at the end of its own independent branch (a separate source, or past a Splitter), never two pools in a row on the same stream. This tripped up an early draft of level 14 (a second pool placed after the first one never filled) before landing on the single-terminal-pool version documented below. This applies to a `"flat"` level's pools too (see Level 20).
- **Geysers.** A geyser only consumes water *while dormant* -- once it activates (see "What's implemented" above) it reverts to plain empty terrain, so its own newly-spawned stream has somewhere to start from. Earlier this session that also meant every later beat from the level's original `water_sources` kept sailing straight through the now-empty cell forever afterward, unless a level went out of its way to catch it (see the retired manual workaround below). **As of 2026-08-10, that's fixed at the engine level**: `HexBoard._is_wall()` treats any coordinate in `active_geysers` exactly like a placed Wall block, so the original feed now automatically backs up and reroutes via its other diagonal there, the same way it would at any ordinary Wall -- it can no longer pass through or land on the geyser cell after activation. The geyser's own new stream is unaffected, since `tick()` injects it directly into the simulation each tick rather than routing it through that same check.
  - **Retired manual workaround (kept for historical/reference purposes -- no longer necessary):** before the fix above, a level had to deliberately place a terminal Pool or Wall immediately after the geyser on the original source's continuing path to catch that leftover feed, or risk an eventual unwanted bottom-edge loss well after the geyser had already served its purpose. Level 18 does exactly this (a terminal Pool right after its geyser) -- it's now redundant given the automatic blocking, but still harmless, so it wasn't removed. New levels no longer need to do this.
- **Dirt ("Dig the River").** An undug dirt cell is a Wall in every simulation-relevant way (`_is_wall()` returns true for it; the placed-block redirect branches skip dirt targets explicitly; `_try_enter()` has a purely defensive DIRT branch that water can never actually reach). The one thing that makes it different from a Wall is that the PLAYER can remove it -- 3 taps via `dig()` -- and that removal is immediate, not queued to the PLACEMENT beat, because "the river lurches forward the instant the third tap lands" is the entire feel of the mechanic. Water waiting against dirt merges into one entry per cell like any pooled water and can't be lost *while it waits* -- but the wait is bounded: 10 unbroken beats of pressing on the same dirt triggers a mudslide (`_note_dirt_stall()` / `_process_mudslides()` / `_trigger_mudslide()`), collapsing a 3-tile downward chain that the water then floods into, wherever it leads. So a dig level's dangers are twofold: *where* a channel gets dug (reaching the bottom row anywhere except a pool is an edge loss), and letting the river sit long enough to route itself. Dig progress lives in `HexBoard.dig_progress` and deliberately keeps its entry at the cap after a cell opens, purely so `_draw_cell()` can keep painting the carved channel in its trench color.

## Playtesting

1. Open the project in Godot, press **F5** (or the Play button, top-right)
2. On the main menu, click **New Game**
3. Pick any slot (they're all empty on first run)
4. Click **Level 1** on the level select screen
5. A popup shows the level's name and a short description of what it does -- tap **Got it** to dismiss it (every other button is unresponsive until you do). Ticking does **not** start automatically after that — you get unlimited time to place blocks first. Click a block button in the bottom bar to select it (its remaining count is shown in parentheses), then click an empty hex cell on the grid to place it there. Click a different block button to switch what you're placing. Tap a cell that already has a block on it to pick that block back up (it's refunded to your inventory) — this works whether or not you have another block type selected. While you're placing blocks, watch the amber arrow chain coming off each water source -- it updates live and shows exactly where that source's water will flow (up to 4 hexes ahead) given your current placements, so you can see whether a diverter actually solves the level before pressing Start. (On a dig level like 21, tapping a brown dirt hex digs it instead -- 3 taps opens it -- and the amber chain extends through each cell you open.)
6. When ready, click **Start** (top-center) — water begins falling from the top, one hex per tick (0.6s), and the fire/pool status updates live. Placing and removing blocks is **not** locked out once ticking starts — you can keep reacting to the water in real time, redirecting a stream mid-flow instead of only planning beforehand. The amber preview arrows disappear the instant you press Start (they reappear if you Retry).
7. **Fires remaining: 0** plus every pool's 4-box status bar fully lit = win. A **Success!** popup appears with a single button -- **Next**, which advances straight into the next level (and shows that level's own intro popup automatically), or **Level Select** on the last level, which returns to the level picker. Losing pops up a small panel over the board showing which specific thing went wrong — "The town flooded!" if water reached a town cell, or "Water overflowed the bottom edge!" if it fell off the grid — with two buttons: **Retry** (resets the level in place, same as the always-visible Retry button at the top) or **Level Select** (returns to the level picker). The top HUD's own **Retry**/**Back** buttons still work at any time too, popup or not.

Two sources: **(0, -4)** flows `"straight"` down column q=0 through its fire at **(0, -1)** into the pool at **(0, 4)**; **(2, -4)** flows `"zigzag"` through its fire at **(1, -2)** -- and needs your **Diverter-Right** at **(2, 0)** to reach its pool at **(3, 0)** (retrofit). Win by tick 13. Verified via a from-scratch Python port of the new `_advance_water_flat()`/`_resolve_block_targets()` logic (the same methodology used for Level 18's reconstruction) -- the port was first checked against Levels 1 and 12 (pointy grid) to confirm the refactor that added the "flat" dispatch branch didn't change pointy-grid behavior at all (both reproduced their previously-verified tick counts exactly), then used to design and confirm this level's fire/pool placements land within the zigzag stream's actual reachable path before it would otherwise drift off the grid's edge (~tick 15). Not yet re-verified through the actual Godot engine, same caveat as everything else in this project to date -- see Known gaps.

### Level 21 — Dig the River: tap the channel forward to the pool
Grid radius 4, zero blocks (`starting_inventory` is empty -- the only tool is your finger). The top three rows are open, so the source at **(0, -4)** zigzags naturally to **(-1, -2)** -- and then hits an unbroken field of packed dirt: every playable cell from row `r = -1` down is `dirt_cells`, EXCEPT a fire at **(-1, 1)** and the terminal pool at **(-1, 4)** on the bottom row. The water backs up against the dirt and waits (dirt holds it like a Wall -- but only for 10 beats at a time before a mudslide takes matters into its own hands), and the player digs the channel forward: **tap a dirt hex 3 times** to open it. The intended channel is the straight down-right chain **(-1, -1) → (-1, 0) → [fire at (-1, 1), no dig needed] → (-1, 2) → (-1, 3) → pool (-1, 4)** -- 4 dug cells, 12 taps, with the fire acting as a free pre-dug gap in the channel that the flow extinguishes on its way through. Any other connected downward channel works too (dirt is freeform); the real hazard is digging a channel that reaches the bottom row anywhere OTHER than the pool -- water spilling past `r = 4` is an edge loss. Verified via the Python-port methodology (18/18 checks): the pre-dug channel wins (measure 12, fire out, pool full 4/4); digging the same channel progressively mid-run (one cell every 2 measures -- the "tap the river forward" play pattern) also wins; a decoy channel dug down the `q = -2` column to the bottom row loses via edge exactly as designed; no digs at all = mudslides now carve the river's own path, ending in an edge loss by measure 29 (the old wait-forever behavior predates the mudslide mechanic); 1-2 taps never open a cell; the flow preview stops at the dirt wall and extends per dug cell; blocks can't be placed on undug dirt (and can on a dug-open cell); and levels 1, 12, and 20 reproduce their previously documented outcomes exactly (regression). Not yet verified through the actual Godot engine, same caveat as everything else to date.

### Level 22 — The Great Cascade: 100 rows, 10 fixed splitters, 11 pools
The biggest level in the game: grid radius 50 (101 rows, ~10x deeper than any prior level), a 5-tile-wide corridor via the new `corridor_half_width = 2` field, and a pure digging level (no inventory). Ten **preset Splitters** are fixed in the riverbed every 9 rows down the corridor's center, and eleven pools await: one on a short side spur off each splitter's left output, plus a final pool on the bottom row. Every corridor cell except the source, the splitters, the pools, and the top two rows below the source (open ground under the 2-row source-clearance rule) is packed dirt (474 dirt cells). The player digs the main channel from the source at **(25, -50)** down through each splitter in turn (each splitter feeds BOTH its outputs every beat, so the side pool and the continuing channel fill/flow simultaneously), digs the 2-cell spur from each splitter's left output to its pool, and finally lets the main channel run into the last pool at **(-25, 50)**. The known solution is 108 dug cells (324 taps); the hazards are digging a channel that reaches the bottom row anywhere other than the final pool, and mudslides -- leave the river pressing on dirt for 10 beats anywhere down the cascade and it collapses 3 tiles on its own. Verified via the Python-port methodology (6/6 checks): the full solution wins with all 11 pools at 4/4 (measure 103); progressive digging (2 cells per measure, top-down -- the real play pattern) also wins; no digs = waits forever with no loss; an extra bottom-row dig beside the final pool loses via edge; splitter cells aren't diggable; and the full 18-check regression suite for levels 1/12/20/21 still passes after the corridor/preset engine changes. Design note baked into the layout: the first draft put each side pool diagonally below the continuing channel, and the pool silently consumed every drop forever, starving the entire cascade below splitter 1 -- caught by the simulation, fixed by moving every side pool onto its own 2-cell dead-end spur 2 columns off the channel. Not yet verified through the actual Godot engine, same caveat as everything else to date.
