## Status: full 100-level campaign -- 78 generated levels, 8 retrofits, task-group Level Select, every level requires interaction (2026-08-17, later same day)

Prompted by: "let's have 100 levels. make sure the player must tap or place atleast 1 tile in any level. group them by task. make later levels have a mix of all elements."

- **Campaign structure (13 task groups)**: Riverbed Basics 1-12, Long Corridors 13-17, Special Waters 18-20, Dig the River 21-22, then the new blocks: Diverter Drills 23-30, Wall Work 31-38, Split Networks 39-46, Town Defense 47-54, Flat Fields 55-62, Geyser Country 63-70, Big Digs 71-78, Jamboree Runs 79-86, The Gauntlet 87-100 (14 escalating corridor levels mixing solution blocks + preset splitters + dirt bands + towns + geysers + budgets, radius 10 -> 20).
- **Generation methodology** (`sim/gen100.py`): solution-first templates -- sample the solution placements on the water's traced path, place pools with a "leak loop" (run the solved trace; every edge-loss adds a pool at the deepest newly-visited cell until the run is leak-free -- pools land off the natural path BY CONSTRUCTION since the idle-run validation rejects self-winning candidates), pick fires from the winning trace's visited cells, grow 4-cell towns on the natural path but off the solved path, drop geysers on the solved path, cut dirt bands across corridors with the dig cells = trace-through-band. Rejection sampling per level (seeded rng, deterministic) until the full validation battery passes: solved run wins; IDLE RUN NEVER WINS in 300 measures (this is what guarantees ">= 1 tap or placement" on every level, mudslides included); 2-row source clearance on every preplaced tile; no placement on sources; width cap respected.
- **The 8 "just watch" levels (2, 4, 6, 8, 9, 13, 18, 20) retrofitted** (`sim/retrofit.py`) -- each now requires exactly one placement. A naive "move the pool one step behind a diverter" failed universally (the natural zigzag reaches the moved pool anyway -- caught by the idle-run check); the shipped retrofits instead re-search each level with the generic machinery, keeping original fires where the new path allows (2, 4, 9, 18, 20) and re-placing them where it doesn't (6, 8, 13). L18's geyser verified to still charge + activate with the new Wall in place; L20 still contrasts straight vs zigzag flat-grid flow.
- **Rounding-parity bug found and fixed before shipping**: Python's round() is banker's, GDScript's roundf() rounds half away from zero -- they disagree on odd corridor rows' band centers, so every corridor computed in the sim differed from the engine's `in_playable_area()` by one column on odd rows. The sim now uses a `round_away()` matching roundf() everywhere; level 22 was REGENERATED with correct centers (splitter columns shifted on odd rows; 474 dirt cells; solution still 108 digs, win@103); all prior suites re-run green. Without this fix, level 22 (and all new corridor levels) would have had dirt/channel cells silently outside the engine's playable band.

- **Verification totals**: 78/78 generated levels validated; 8/8 retrofits validated; then a full END-TO-END pass (`sim/verify_shipped.py`) that re-parses every shipped `.tres` text file back into the sim and re-validates all 100 against their solutions -- 100/100 passed (this catches emitter bugs, not just design bugs). ## Status: placement rules -- no blocks on sources + 2-row clearance for preplaced tiles; levels 1/2/4/8/10/11/12/22 adjusted (2026-08-17, later same day)

Prompted by: "lets not put user placeable tiles on water sources. any preplaced level tile should be no closer than 2 rows vertically from starting water sources."

- **Engine rule (`HexBoard.place_block()`)**: rejects any coord in `level_data.water_sources` OR `active_geysers` (an activated geyser IS a source), checked before everything else. Mirrored in the Python sim.
- **Authoring rule (audit, not code)**: every level-shipped feature tile (fire/pool/town/geyser/dirt/preset block) must satisfy `|r_tile - r_source| >= 2` for every starting source. `blocked_cells` exempt (grid shape, not a tile). A per-level audit table in `verify_rules.py` enforces this for levels 1-21; level 22's generator enforces it structurally.
- **The big consequence, caught before touching any files**: on the pointy grid, water's `q` can NEVER increase (DOWN_LEFT is q-1, DOWN_RIGHT is q+0), and every stream's first move is forced down-left -- so the only way to reach right-column cells like level 1's fire at (0,-2) was a block ON the source, exactly what the new rule forbids. Replacement technique: **Wall at the source's first landing cell** ((-1,-3) for a (0,-4) source) -- the blocked first step makes the drop retry its other diagonal, sending it down the RIGHT column (q unchanged) permanently. This reaches the same cells the on-source diverter used to, without touching the source, and conveniently keeps the same win tick counts.
- **Level changes**:
  - L1: data untouched (its tiles already satisfied the 2-row rule); documented solution changed to Wall at (-1,-3) (its inventory already included a wall). Win tick 8, unchanged.
  - L2/L4/L8: one fire each moved a row down onto the same natural path ((-1,-3)->(-1,-2), (0,-3)->(0,-2), (-1,-3)->(-1,-2)) -- all still zero-block wins at their original tick counts (8/8/9).
  - L10: inventory gains a wall (keeps a spare divert_right); solution = Wall at (-1,-3). Win tick 11, unchanged. Intro updated to teach the bounce technique.
  - L11: inventory = wall + splitter (+ spare divert_right); solution = Wall at (-1,-3) + Splitter at (1,-2) (splitter half unchanged). Win tick 11, unchanged.
  - L12: fully relaid -- town moved to {(-2,-1),(-2,0),(-3,0),(-3,1)} (on the natural path, 3+ rows below the source, still 4 edge-connected cells), fire (-1,-1), pool (-1,0); inventory wall + spare divert_right; solution = Wall at (-1,-3). Unsolved now loses via town on tick 3 (was tick 1); solved wins tick 8 (unchanged). Intro rewritten.
  - L22: regenerated -- dirt now starts 2 rows below the source row (474 dirt cells, was 483; solution 108 dug cells / 324 taps, was 109/327), the water crossing the open clearance naturally before meeting the first dirt. All other geometry identical.

Main suite updated for the new L1/L12 solutions: 19/19. Mudslide suite 10/10, level-22 suite 6/6 -- 52 checks total, all green.

## Status: mudslide mechanic -- stalled water collapses 3 dirt tiles; pre-start digging confirmed (2026-08-17, later same day)

Prompted by: "in these levels make sure the player can start digging the dirt before pressing the start button. lets add a mudslide mechanic. when the water is sitting at a dirt tile too long then 3 tiles of dirt collapse."

Design decisions confirmed via follow-up questions: threshold **10 beats** (~3s at current tempo); the collapse is a **downward chain of 3** dirt tiles starting with the blocking tile; collapsed tiles are **fully open, distinct wet-mud color** (darker than the player-dug trench color), so the board shows where the river forced its own path vs. where the player chose it.

- **Pre-start digging**: already worked -- `Level.gd`'s `_handle_tap()` has never been gated on `started`, so dirt can be dug the moment the intro popup is dismissed (and the flow-preview arrows extend live per dug cell). No code change needed; confirmed rather than assumed.
- **`claude/game/scripts/gameplay/HexBoard.gd`** — the mudslide:
  - New consts `MUDSLIDE_BEATS_REQUIRED := 10`, `MUDSLIDE_COLLAPSE_TILES := 3`, `MUDSLIDE_COLOR` (wet mud). New state: `dirt_stall` (coord -> consecutive stalled WATER beats), `_stalled_this_beat` (rebuilt each WATER beat: coord -> preferred collapse dir), `mudslide_cells` (collapsed-by-slide cells, for the mud color). All cleared on setup()/retry.
  - **`_note_dirt_stall(coord, dirs)`** called from all four stay-put paths (pointy natural fallback, pointy block-all-targets-dirt, flat natural fallback, flat block-all-targets-dirt) -- records a stall ONLY if at least one tried direction is blocked specifically by undug dirt (ordinary Wall/edge backups never slide). First dirt direction found = the slide's preferred direction.
  - **`_process_mudslides()`** runs at the end of every WATER beat, after all drops have moved (so terrain changes can't affect drops mid-loop): prunes counters for coords no longer stalled (water moved on / player dug the blocker -- the clock only counts UNBROKEN stalls and restarts from zero), increments current stalls, and fires the slide at 10 (resetting that counter, so a still-stuck drop starts a fresh 10-beat clock toward the NEXT slide).
  - **`_trigger_mudslide(from, dir)`**: collapses up to 3 undug dirt tiles -- the blocker first, then continuing in the slide direction, falling back to the grid's other downward option(s) when the preferred one isn't dirt, stopping early if no dirt continues the chain. Each collapsed tile: terrain -> EMPTY, `dig_progress` -> cap (renders as opened), `mudslide_cells[cell] = true`. The freed water floods the collapsed channel on the very next WATER beat, wherever it leads.
  - `_draw_cell()`: new `mudslide_cells` branch (MUDSLIDE_COLOR) checked before the dug-trench branch.
- **Level intros updated**: `level_021.tres` / `level_022.tres` intro_text now warns about the mudslide.
- **Behavior change worth knowing**: idling on a dig level is no longer safe. Level 21 with zero digs used to wait forever; now mudslides carve the river's own path and it loses via edge on measure 29 (after 2 slides). Level 22 idle just slides slowly down the corridor (still nowhere near the bottom after 120 measures). The README's several "water can never be lost while waiting against dirt / safe indefinitely" claims were all corrected.
- **Verification**: new 10-check mudslide suite passed (no collapse at 9 beats / fires exactly at 10; exactly 3 tiles collapse, fully open, at dig cap; chain starts adjacent below the stalled water and descends one row per tile; water advances through the slide; an early dig prunes the stall counter with no phantom slide; L21 idle now ends via edge with slides; L21 dug-normally still wins with ZERO mudslides -- staying ahead of the water is untouched). Full regression: main suite 18/18 (one check updated: L21-idle expectation changed from wait-forever to mudslide-edge-loss, by design), level 22 suite 6/6 (its idle check still times out safely within its 120-measure window -- slides advance only ~3 cells per ~13 measures down a 101-row corridor).
- **Not yet done**: live playtest of the slide's feel (is 10 beats right? does the mud color read?); no slide animation/sound/screen-shake cue yet (fits the beat-locked audio backlog); possible warning telegraph (e.g. the pressed dirt tile trembling as the counter climbs) -- not asked for yet, worth considering since the player currently gets no visible countdown.

## Status: new "Dig the River" level type -- tap-to-dig dirt terrain + demo level 21 (2026-08-17)

Prompted by: "lets make another level type. called dig the river. this is one where the player has to tap a hex 3 times to allow the river to flow forward. the goal is to tap the river all the way to the pool"

Design decisions confirmed via follow-up questions: diggable cells are **author-placed** (a new `dirt_cells` terrain array on LevelData, not "any empty hex"); water meeting undug dirt **tries the other downward tile and goes there if open** (i.e. dirt behaves exactly like a Wall toward natural fall -- retry-other-diagonal -- and water backs up and waits only when every candidate is blocked, never losing while it waits); digging is **free, unlimited, any time** (before or after Start, no inventory cost); dig-progress feedback is **color stages only** (no status bar, no counter glyph).

- **`claude/game/scripts/resources/LevelData.gd`** — new `@export var dirt_cells: Array[Vector2i] = []` (empty default, so all 20 existing levels are untouched), with authoring notes in its doc comment.
- **`claude/game/scripts/gameplay/HexBoard.gd`** — the bulk of the feature:
  - `CellState.DIRT`, `DIG_TAPS_REQUIRED := 3`, `DIRT_COLORS` (3 brown stages: packed / loosened / almost-through) + `DUG_TRENCH_COLOR`, and `dig_progress: Dictionary` (Vector2i -> tap count; initialized to 0 per dirt cell in `setup()`, so Retry fully re-packs all dirt).
  - **`dig(coord) -> bool`** — one tap; the 3rd tap reverts the cell's terrain to `EMPTY`. Returns false for non-dirt cells so `Level.gd` can simply try-dig first and fall through. Deliberately **immediate** (NOT queued to the PLACEMENT beat like block placement) -- the "tap the river forward" feel depends on water being released the instant the third tap lands. The `dig_progress` entry deliberately STAYS at the cap after opening, so `_draw_cell()` keeps painting the carved channel in the trench color -- the dug riverbed stays visible against ordinary empty cells.
  - **`_is_undug_dirt()`** helper + **`_is_wall()` now returns true for undug dirt** -- this one hook makes natural fall on BOTH grid orientations treat packed dirt exactly like a Wall (retry other diagonal; back up if boxed in), with zero changes to the natural-fall functions themselves.
  - **Both placed-block redirect branches** (`_advance_water()` pointy + `_advance_water_flat()`) now skip undug-dirt targets, and if EVERY target of a Diverter/Splitter is undug dirt the water backs up on the block (previously unreachable case; without this a Diverter aimed at dirt would have called `_try_enter()` straight into it).
  - **`_try_enter()` got a defensive DIRT branch** (return false, no side effects, never a loss) -- callers filter dirt out beforehand, this is belt-and-braces.
  - **`place_block()` rejects DIRT** terrain (same rule as fire/pool/town/geyser). Digging a cell open makes it placeable again like any empty cell.
  - **Flow preview is dirt-aware for free** via `_is_wall()` on the natural-fall path, plus an explicit undug-dirt skip in `_predict_branch()`'s placed-block loop -- an undug dirt cell silently ends a preview chain like a Wall, and digging pre-start live-extends the amber arrows through the opened cell on the next redraw.
  - **`_draw_cell()`**: DIRT branch picks from `DIRT_COLORS` by tap count (color stages only, per the design decision); a new trailing `elif` paints fully-dug cells (`terrain == EMPTY` but `dig_progress` at cap) in `DUG_TRENCH_COLOR`. No icon glyph for dirt, by design.
- **`claude/game/scripts/gameplay/Level.gd`** — `_handle_tap()` now tries `board.dig(coord)` FIRST, before block pickup/placement; dig() returning false makes it a no-op on every non-dirt cell/level. No inventory refresh needed (digging is free). Existing tap-vs-drag threshold handling is untouched -- a scroll drag still doesn't count as a dig tap.
- **`claude/game/data/levels/level_021.tres`** (new) + `LEVEL_PATHS` in **`LevelSelect.gd`** extended — "21. Dig the River", grid radius 4, source (0,-4), zero starting inventory. Top three rows open (water zigzags naturally to (-1,-2)), then EVERY playable cell from row r=-1 down is dirt (41 cells) except a fire at (-1,1) and the terminal pool at (-1,4). Intended channel: dig (-1,-1), (-1,0), (-1,2), (-1,3) -- the fire is a free gap in the channel -- 4 cells / 12 taps. Freeform: any connected downward channel works; the hazard is digging to the bottom row anywhere other than the pool (edge loss). Water waiting against dirt can never be lost, so the undug board is safe indefinitely.
- **Verification**: no live Godot engine in this environment; verified via the established from-scratch Python port methodology (`Board` class porting both grid styles' advance logic + the dig mechanic + the preview predictor). **18/18 checks passed**: regression -- L1 solved wins measure 8 / unsolved edge-loss, L12 unsolved town-loss measure 1 / solved wins measure 8, L20 flat no-blocks wins measure 14 (all matching previously documented outcomes exactly); L21 -- no digs = 60-measure timeout with NO loss (water waits); pre-dug channel wins measure 12 (fire out, pool 4/4); progressive mid-run digging (one channel cell every 2 measures -- the actual "tap the river forward" play pattern) also wins; decoy channel dug down q=-2 to the bottom row loses via edge; 1-2 taps never open a cell, 3rd tap does, digging non-dirt rejected; preview stops at dirt and extends per dug cell; block placement rejected on undug dirt, allowed once dug.

New `_scroll_to_bottom()` (called at the end of `_build_level_buttons()`) starts the `ScrollContainer` scrolled all the way down, so the screen opens on Level 1 and the player scrolls up to reach higher levels -- a "climb the mountain" feel instead of the usual top-down list. - **Why the scroll needs a frame delay**: `_scroll_to_bottom()` `await`s one `process_frame` before setting `scroll.scroll_vertical` -- `ScrollContainer` doesn't know the `VBoxContainer`'s full content height until a layout pass has actually run after the 100 buttons were just added in the same call, so setting the scroll position synchronously would clamp against a stale (possibly zero) content size and leave the view stuck at the top. The value set afterward (`1000000000`) is deliberately far past any real maximum -- `ScrollContainer` clamps `scroll_vertical` to the true max automatically, so this reliably lands at the bottom regardless of exactly how tall 100 rows turns out to be.
- **Verification**: no live Godot engine is available in this environment. Verified by inspection: the reversed loop bounds correctly place index `0` (Level 1) as the last `add_child()` call and index `TOTAL_LEVEL_SLOTS - 1` (slot 100) as the first; `await get_tree().process_frame` inside a non-async caller (`_ready()`, `_on_debug_unlock_toggled()`) is valid GDScript -- the call returns immediately at the await point and the deferred scroll runs on the next frame without blocking the caller.

## Status: split the tick into a 4-beat cycle (placement/water/terrain/status), constant sub-tick clock (2026-08-10, later same day)

Prompted by a design conversation about giving the game a felt sense of musical rhythm: water advances on beat 2 of a 4/4 measure, with beats 1, 3, and 4 given their own jobs (placement, terrain resolution, status reveal) instead of everything resolving on one flat tick. Also prompted by "the ticks should be constant, the ticks per beat will change in the game" -- i.e. the engine's base clock should stay fixed, with tempo expressed as how many of those constant ticks make up one beat, not by changing the clock itself.

- **`claude/game/scripts/gameplay/Level.gd`** — replaced the single `TICK_INTERVAL := 0.6` constant/`_on_tick()` pair with `SUBTICK_INTERVAL := 0.15` (a constant engine heartbeat) plus `var ticks_per_beat: int = 4` (the tempo knob -- fewer ticks per beat means a faster beat, without ever touching `SUBTICK_INTERVAL`). `4 * 0.15 = 0.6`, so the starting feel matches the old flat-tick pacing exactly; changing tempo later is just reassigning `ticks_per_beat`. New `enum BeatPhase { PLACEMENT = 1, WATER = 2, TERRAIN = 3, STATUS = 4 }` and `current_beat`/`_subtick_count` track position in the cycle. `_on_subtick()` fires every `SUBTICK_INTERVAL` and only advances the beat every `ticks_per_beat`-th fire (via new `_advance_beat()`, which dispatches to one of four new `HexBoard` phase methods and then wraps `current_beat` 1→2→3→4→1). `_on_retry_pressed()` resets `current_beat`/`_subtick_count` back to the start of the cycle.
- **`claude/game/scripts/gameplay/HexBoard.gd`** — the old single `tick()` function is gone, replaced by four phase methods:
  - **`resolve_placement_phase()`** (beat 1) commits queued block placements/removals to `placed_blocks`. Placement itself is no longer instant: `place_block()`/`remove_block()` now validate and reserve inventory/budget immediately (so the inventory bar still reflects availability right away, same as before) but queue the actual board mutation into new `pending_placements`/`pending_removals` dicts, only committed here on the next PLACEMENT beat. A tap mid-measure is buffered, not rejected -- the player doesn't need to time taps to the beat.
  - **`resolve_water_phase()`** (beat 2) is the renamed core simulation step -- spawns/advances water exactly as the old `tick()` did, and is the one phase that still redraws immediately (water position is meant to visibly snap on this beat). Terrain contact (fire/pool/geyser) is no longer resolved inline here.
  - **`resolve_terrain_phase()`** (beat 3) applies the fire-extinguish/pool-fill/geyser-fill effects for cells flagged during beat 2 (new `_pending_terrain: Array[Vector2i]`, populated by `_try_enter()` instead of mutating state directly, consumed by new `_resolve_terrain_contact()`). Deliberately does NOT call `queue_redraw()`.
  - **`resolve_status_phase()`** (beat 4) calls `_check_end_conditions()` (win-check now runs after terrain is finalized) and is the one that finally calls `queue_redraw()` -- holding the redraw back from beat 3 to beat 4 is what makes a pool's status-bar box flipping or a fire going out visibly land on the STATUS beat specifically, per the "status bar tiles update on beat 4" design decision, without needing any partial-redraw machinery.
  - `_try_enter()` still resolves town-contact and edge-of-board loss immediately during the WATER beat (beat 2) rather than deferring them to TERRAIN -- those read as "the water left the play area" rather than "terrain reacting to contact," so there was no reason to hold them back a beat.
- **Design decisions made without re-confirming, flagged here in case they need revisiting**: (1) town/edge loss stays on beat 2, not deferred to beat 3, per the reasoning above; (2) a placement/removal tap is buffered and applied on the next beat 1 rather than requiring the player to tap exactly on-beat, favoring a forgiving mobile-friendly input model over strict rhythm-game timing; (3) `SUBTICK_INTERVAL`/`ticks_per_beat` were chosen to reproduce the old 0.6s-per-beat feel as a safe starting point, not tuned to the 72/80 BPM figures in the "Music-driven timing spec" section of `toolset-and-requirements.md` -- mapping real BPM values onto `ticks_per_beat` is still open.
- **Not yet done**: no live Godot playtest (as with everything else in this project to date, this was written and reasoned through without a live engine available) -- especially worth confirming that buffered placement doesn't feel laggy/unresponsive in practice, and that the beat-4-deferred-redraw actually reads as intentional rather than like a rendering delay. Per-sub-tick animation/audio pulses (the original spec's stated purpose for sub-ticks) aren't wired to anything yet -- `_on_subtick()`'s early-return path is a no-op hook. Mapping the 72/80 BPM tempo spec onto `ticks_per_beat` per level, and any mid-level tempo-shift mechanic discussed alongside this, are still open follow-ups.

## New feature: "Jamboree" free-choice block budget
Prompted by: "lets do another type of level where its a long scrolling level but the user gets to place a total number of tiles but of any variety they want. jamboree level"

- **`LevelData.total_block_budget: int`** (default 0): a level-level switch. 0 (the default) keeps the existing per-block-type `starting_inventory` behavior unchanged. Any positive value instead grants the player one shared pool of that many total placements, with no per-type limit -- any block from the full catalog, in any combination, as long as the running total placed never exceeds the budget. `starting_inventory` is ignored entirely in this mode.
- **`HexBoard.gd`**: added `use_block_budget: bool` (set once in `setup()` from `data.total_block_budget > 0`) and `block_budget_remaining: int`. `place_block()`/`remove_block()` branch on `use_block_budget`: in budget mode they decrement/increment `block_budget_remaining` regardless of which block type is placed/removed, instead of touching `inventory` (which is left empty and unused in this mode); in the old mode, behavior is byte-for-byte unchanged from before.
- **`Level.gd`**: `_build_inventory_bar()` now builds its buttons from `block_catalog.keys()` (every block type that exists) instead of `level_data.starting_inventory.keys()` when `board.use_block_budget` is true, and shows/hides a new `BudgetLabel` accordingly. `_refresh_inventory_labels()` branches the same way: in budget mode every button just shows the block's display name (no per-type count, since there isn't one) and all buttons disable together the instant `block_budget_remaining` hits zero; the label reads `"Tiles left: N"`. Non-budget levels are unaffected -- same per-type `"Name (count)"` labels as before.
- **`scenes/Level.tscn`**: added a `BudgetLabel` node (`UI/HUD/BudgetLabel`, `visible = false` by default, positioned just above the inventory bar) that only becomes visible for a Jamboree level.
- **New level 19** (radius 10, 21 rows, `total_block_budget = 3`): the first tall scrolling level built with the free-choice budget instead of a fixed inventory. Only one placement is strictly required to win -- a Diverter-Left at `(-1, 1)`, rerouting the natural path around a 4-cell town blob at `(-1, 2)` -- with two fires (one pre-diversion, one post-diversion, both auto-hit by the rerouted flow) and a terminal pool at the diverted branch's bottom landing cell `(-6, 10)`. The 2 spare budget tiles are deliberately unnecessary, there for the player to experiment with (place a Splitter+Wall combo off the main flow, etc.) without being required -- demonstrating the "any variety, not a prescribed loadout" flavor the mode is meant to convey. `LEVEL_PATHS` in `LevelSelect.gd` extended.
- **Headless verification**: a dedicated trace (deleted after use) confirmed the diverted branch's exact landing cell before placing the pool there; a positive test confirmed the level wins by tick 25 with the diverter placed, and a negative sanity test confirmed it correctly loses (`lose_reason == "town"`) by tick 13 with no blocks placed at all -- i.e. the diverter is actually load-bearing, not decorative. A full 1-19 regression re-run afterward confirmed every other level's setup/simulation is untouched (levels 1-18 "fail" in that raw regression only because it doesn't place their per-level solution blocks -- expected, and unrelated to this change; level 19 is the only one the regression script actually plays out end-to-end, including its solution).
- Along the way, hit and fixed two authoring gotchas worth remembering for future levels: (1) a trial `LevelData` with zero `fire_cells` and zero `pool_targets` triggers an instant, premature `_win()` on tick 1 (vacuously "all pools full" with none to fill) -- any throwaway/tracing script needs at least one deliberately-unreachable dummy fire cell to avoid `game_over` short-circuiting every subsequent `tick()` call. (2) A block's "off-branch" (e.g. a Splitter's second target) that terminates in a Fire looks safe at first but isn't: once that fire is extinguished by the first arrival, the cell reverts to plain empty terrain and every later arrival keeps falling from there via ordinary natural zigzag -- if nothing permanently catches it (a Wall, or it happens to complete the win first), it can cause a bottom-edge loss well after the fire's already out. Level 19 sidesteps this by keeping its only required block a Diverter (which has no "off-branch" to leak from) rather than a Splitter.
